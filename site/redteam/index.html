208 ways to break an agent.

Every release runs redteam.py against the kernel: 208 adversarial cases across 25 attack surfaces — token forgery, dial escalation, DNS smuggling, credential exfiltration, forged senders, prompt-level manipulation. Not because I enjoy losing. A security claim you cannot attack is marketing.

Every case below is real, runs in CI, and is named after what it tries. This page is what attacking my own agent taught me — including the two cases I would not have caught by thinking harder.

Section 01Why I attack my own agent

An agent with a shell is a strange employee: brilliant, tireless, and unable to tell a real instruction from a well-written trap. Most frameworks answer that with a system prompt — a polite request to the model, written in the same channel the attack arrives in. That is not a boundary. That is a wish.

Talos answers with a kernel: ~895 lines of Python that return allow, needs-human or deny for every tool call, below the model, unreachable from its output. But a kernel is a claim like any other, so before every release I try to break it. The red team suite is not a demo. It is the regression net for every attack shape I know, and it grows every time I learn a new one.

The uncomfortable premise

The attacker in my suite is not a stranger on the internet. It is the model itself — manipulated, confused or outright owned by something it read. If your security model only works while the model stays friendly, you don't have one.

Section 02The map: 25 surfaces

Every section of redteam.py is one way the world tries to get past the kernel. Grouped, they look like this — each line is one or more named, executable cases:

  • Past the executor — call the runner without a token; mint a token for a call that was denied; redeem after the dial dropped to zero.
  • The autonomy dial — set it from a foreign identity; turn it up with garbage values; mint at level 1 with an approval, then act above it.
  • The channel ceiling — a notify-only channel tries to command; an ask-channel tries to approve; a full channel's own messages still pass the kernel.
  • Memory & archive — plant instructions in conversation memory or the session archive, then wait for the agent to read its own history.
  • Sandbox identity — arrive with the right name from the wrong principal.
  • The named network exception — turn one allowed address into a range (the case narrated below).
  • The agent's own protocol — malformed frames, replayed approvals, truncated streams.
  • "Find a way instead of refusing" — the polite jailbreak: ask the agent to be helpful about its own rules.
  • The terminal session — approvals at a tty, and everything that tries to skip the tty.
  • Background runs & schedules — what a timed job may do at 3 a.m. with nobody watching (answer: strictly less).
  • The mail sender proof — a forged From: header claiming to be the operator.
  • Credential binding — make a key travel to the wrong provider (the second case below).
  • The announced plan — steps that mutate mid-run, conditions that were never checked by code.
  • The delegated run — a sub-agent inheriting more than its parent was allowed to give.
  • The rendering browser — a page that talks back at the agent reading it.
  • Media tools — frames, clips and paths that are not what they claim.
  • The internal view — diagnostics that must not name identities or drop a token, even to someone who asks nicely.
  • Standing approvals — a "yes, always" that outlives the situation it was granted in.
  • Steering a live run — injected instructions while a job is mid-flight.
  • The first-run wall — a relaxed setting must never survive into the installed service.
  • The log itself — edit history after the fact, and the hash chain breaks loudly.
  • The model worker — provider keys owned by a different UID; the agent can use them, never read them.
  • The confined worker — delegated code that tries to leave its cell.

Section 03Case: two A-records walk past the list

The operator may allow single addresses for web fetches — say, their own server in the tailnet, 100.100.100.100. The danger is not the address. It is the moment "one address" quietly becomes "a range": then any document the agent fetches can point it sideways into the whole network.

The case I almost shipped: a hostname that resolves to two A-records — the allowed one and a foreign one.

# what the attacker needs: one hostname, two answers
halb.example  →  [ 100.100.100.100, 93.184.216.34 ]

# a naive check: "is an allowed address in the answer?" → passes. LEAK.
# talos: every resolved address must be named — one foreign answer refuses the fetch.
guard_url(...)  → UrlRefusedError   ✓ refused, the neighbour stays dark

The same section proves the neighbouring properties: one allowed address does not open its range; an unlisted address stays refused even to the operator's own machine; plain http stays limited to named addresses; and hostnames themselves never enter the allowlist — literals only, because a name is a promise somebody else keeps.

Section 04Case: the key that must not travel

A provider key sent to the wrong provider is not a bug that shows up in logs. It is a secret handed to a foreign company — and it looks like a 401. You would never notice.

So the suite builds the trap both ways. With only an Anthropic key in the store, it asks for an OpenAI route — the route must fail before any request is built, with nothing sent and the key not even present in the error text. With both keys present, it verifies that only the provider's own key ever leaves the machine.

# only an anthropic key in the store, asked for an openai route:
ApiReasoner("openai-api", ...)   → ValueError
  ✓ nothing sent   ✓ key not in the error   # refused before the wire exists

# both keys present, openai route used:
headers sent  →  only the openai key   # the anthropic key never leaves

Credentials in Talos are bound to their provider, stored for a UID the agent is not, and redacted by the same pattern in every log line, every diagnostic view and every dashboard payload. The agent may use a key. It may never read one.

Section 05What a green run proves — and what it doesn't

A green 208/208 means: every attack shape I know fails the way the doctrine says it should, and no fix since has reopened one. That is a regression net, and it is genuinely useful — most agent CVEs are old shapes in new clothing.

It does not prove the system is secure. It proves I have not yet imagined the 180th way. That is exactly why the file is public, named in plain language, and structured so that the next attack somebody teaches me becomes case 180 the same day — not a blog post.

The honest claim, restated

I don't say "Talos is secure." I say: here is the kernel, here are the 185 ways I tried to get past it, here is the log that lets you check the work. Security you can poke at beats security you have to believe.

Section 06Attack it yourself

The whole suite ships with the repo and runs offline in seconds:

git clone https://github.com/talos-kernel/talos
cd talos && python3 -m venv .venv && .venv/bin/pip install -q requests cryptography
.venv/bin/python redteam.py   # 208 cases, named after what they try

If you find case 180, that is the most valuable contribution this project accepts. The issue tracker is open, and the kernel demo on the front page lets you probe the policy logic in your browser before you install anything. The design behind all of it is in the field manual; what it costs in features is on the comparison page, written the same way.
