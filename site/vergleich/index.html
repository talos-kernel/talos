The others can do more.

That is not false modesty. It is the first fact on this page. OpenClaw and Hermes have more channels, more skills, browser automation and mature cron fleets. If that breadth is what you are after, you are better served there. I will not talk it away.

Talos trades breadth for something else: a deterministic policy kernel between model and effect, a sandbox around the shell, and a log whose integrity you can prove instead of having to believe. The gap is doctrine, not backlog. That is what this page is about.

If you are looking at an OpenClaw alternative or a self-hosted Hermes-style agent because you want to hand an agent a shell without handing it your trust model: that is what I built Talos for. Same league of autonomy — sub-agents, MCP, scheduled runs, browser work, live dashboard — but every effect passes one small kernel first, and the agent can never grant itself anything. §1 · where the others lead

What OpenClaw and Hermes do better

The other side first, in full. If you run either project, nothing you use every day should be missing here.

  • Channels. Several messengers, companion apps, media pipelines for images, audio and documents. Talos has four ways in (Telegram, mail, CLI, WhatsApp over an operator-controlled broker) — and all four only fetch.
  • Skills and plugins. Catalogues in the hundreds, from calendars to image generation. Talos has 26 tools, worker-confined MCP behind an operator-owned registry, and a sub-agent DAG — and the number grows slowly, on purpose, see §3.
  • Browser automation. Filling in forms, clicking, driving entire flows, as a first-class tool. The Talos browser renders and reads; automation exists only inside the confined worker (MCP, double opt-in), never as a native tool.
  • Everyday automation. Cron fleets, watchdogs, morning reports — both projects have matured here. Talos ships installable blueprints and a live dashboard, but every schedule runs under a hard ceiling (§3).
  • Model routing. Multiple sources, local models, mature fallback chains. Talos has provider routes with fallback — solid, but narrower.

Both projects also move faster. There, a new capability is a feature question. Here it is a kernel question: every new tool needs a verdict that survives 206 adversarial cases.

§3 · why deliberately less

Every missing row has a reason

None of this is backlog. Every entry was considered and rejected, and the boundary next to it is held by a red-team case. Retrofit one of these rows and you are not building Talos plus a feature. You are building a different product.

inbound webhook Every way in fetches: Telegram long-polls, mail is pulled over IMAP, WhatsApp is pulled over SSH from an operator-controlled broker. A webhook needs a port the world can reach — an outbound-only process would become a reachable one. That is why the Cloud-API WhatsApp variant stays delivery-only, and why the broker variant pulls instead of listening. Deliberate, not “not built yet”.
browser automation Clicking, typing and submitting have no derivable target — the kernel could not judge what is about to happen. A tool without a target is DENY by construction. So browse renders and reads, inside the resolver cage, so that even a redirect cannot leave the host that was checked.
skill catalogue Breadth is cheap — gated breadth is not. Every tool needs a declared effect and a target extractor, otherwise there is nothing to judge. The 26 tools are the ones where the kernel can justify every verdict; tool number 26 had to pass the same test.
yolo mode The autonomy dial can only ever tighten, never widen. A mode that grants rights next to the kernel would be a second source of permission — exactly the problem capability tokens were built to remove.
plan approval Approving a plan would mean approving actions nobody has seen. A plan may set an order and an abort condition; every step still passes the gate on its own. A plan can only end a run earlier, never allow anything.
cron fleet Unattended means: NEEDS_HUMAN becomes DENY. A question dropped into a chat where a different conversation is going on is the most reliable way to land a “yes” on the wrong thing. That is why the schedule list looks short — it runs under the ceiling, not above it.

The short version: the model proposes, it never decides. What would soften that order is not missing. I rejected it. Feature parity with OpenClaw or Hermes is explicitly not a goal.

§5 · which agent for what

The honest recommendation

OpenClaw or Hermes,

if an agent is meant to carry your day-to-day: messengers in both directions, browser flows, a broad skill catalogue, automation around the clock. That breadth is real, it has matured, and Talos will not offer it.

Talos,

if an agent gets a shell on a machine where something can break — and it must be provable afterwards what it did and what it did not. Kernel, sandbox, hash chain: that is what I built it for, and little else.

No contradiction

Running both at once is the obvious split: the broad agent for the work, the narrow one for the machine you hand a shell to. This page is meant to sharpen the choice, not make it for you.
